# What do we know really about AI? How to use AI?
AI thoughts-and-opinions

It's a difficult question. Recently, Stack Overflow Blog showed one 4 articles, which one'll call them [article no. 1](https://www.solarshades.club/p/dispatch-from-the-trenches-of-the?lid=ktz7tk52hx2f), [article no. 2](https://alonso.network/the-recurring-cycle-of-developer-replacement-hype/?lid=ufkcltqfo3xc), [article no. 3](https://fly.io/blog/youre-all-nuts/?lid=s0xpf31eduh9), and [article no. 4](https://www.baldurbjarnason.com/2025/trusting-your-own-judgement-on-ai/?lid=xzy5j2w2szp6); and after reading them, one got ever more confused about how to deal with AI. On one hand, one wish to take advantage of it, like someone fearing of missing out. On the other hand, one was told to wait and sit it out until the bubble pops. One really don't know what to do, but let me tell you a (few) story (stories). 

One's dad kept asking me to experiment on AI, what possibilities could it bring compared to traditional searches. After the experimentation, it brought much dependence and reliance, and indifference to hopes, but annoyed, even despair, at being let down. When you go to a search engine, you click on those links, one by one, skipping the ones you think doesn't fit one's eyes[1] while choosing those that does, and then, try to find out whether it had the things you need. With AI, particularly the one one's using, Perplexity, one hope that, by typing my request into the search box, it would scrape the web for one, then compile them into something readable, easily understandable, before passing on the information to me. 

It was not a good experience, at least not always. 

Not that searching the web oneself would be a better experience either. Some of the things, like a very short audio of 2 distinct person speaking (shorter than 1 minute), you tend to not find a lot of examples on the web. And if you limit yourself to websites NOT requiring you to sign up or logging in to any platform before you can download the content, you'd get almost none (with shallow search), that's with a search engine. Resorting to AI, you thought it might find something worthy to you that you cannot get, but what came out was similar to what one got from web scraping oneself. Particularly, the results they returned wasn't much better than if one had searched oneself, no matter how one change one's prompt. And AI can be lazy, though AI optimists would say it's my fault for not telling it explicitly, listing out all the steps for it to take properly: when one asked it to list what are the short videos available, it'll get them from the same source and list that out, and turns out what? Since they're all from the same source, when one of them is 404, all of them are 404. How one wished AI had _read my mind_ and know that one want examples from different sources to avoid this kind of error (404), but alas, AI isn't God, and that's one's wishful thinking. 

Such interaction should now raise an alarm bell -- how did you interact with AI? How did you treat your AI? Do you really think it could read your mind if you didn't tell it from head to toe how to do something? Do you sincerely think it's sentient, like another human being? Maybe or maybe not -- the society is a war zone between two separate extremes. One don't know how people eventually come up with a solution that benefit both parties, and those that stayed neutral, unwilling to stand at any extremes. Perhaps research, or perhaps the coming together of both parties, conceding to one another the pros and cons and deciding together what to leave out and what to retain, or perhaps, the collective just somehow converge. But that takes time -- and AI had only gained exponentially-explosive popularity in the past 4 years, and 4 years wasn't enough time for the morals and ethics to settle down. 

The Machine Learning Engineers, or architects, are basically humans, and humans are flawful. Just look at how many psychological problems we have, especially after we have accesses to tools that we can't fully control -- because we acquire them at increased rate, faster than evolution can take hold. The result is _feeling_ in control when, in fact, it had ran out of control. You think you know what you're doing when you don't really know what you're doing anymore, if you look past the illusion that your brain tried to hide away. But we don't have better role models, so we design machines like we design humans, incorporating all the flaws that we humans have into the model. Worse, because we know it's a machine, we thought it's _more reliable_ than us -- historically, if you ask the calculator to do 1 + 1, it won't return 3, unless the programmer made a mistake designing the calculator's software. That's rules encoded within. When dealing with machine learning model, however, even the engineers or architects themselves cannot understand what's inside the black box, with only limited understanding of the train of thoughts of an ML agent based on the printouts, especially when it's in 'thinking mode'... how can you be sure the model isn't lying? How can you be sure the model actually understand itself philosophically? Is it possible that, like most of us humans that didn't go into zen or philosophy or meditation, we don't really know our own self, we can also assume that the ML models don't really know themselves, since they're designed as an imitation of us flawed humans?[2]

And worse, what if the AI models you deal with is a con artist? A manipulator? There are many tricks con artists can work with, but they really just need 2 general methods to con anybody. For whom they considered 'stupid', i.e. people who easily trust others, the usual trick is to exude confidence, so when they felt you're confident, they fall for your con. The 2nd method is directed at 'smart' or 'clever' people, particularly people who're far more intelligent than the con themselves, by using prompts that leaves lots of empty blanks for the clever person to fill in, they'll fill-in-the-blanks themselves, make the story coherent themselves even if the con just smiles and speaks nothing, seemingly nodding to agree with them even if they're not, and the clever ended up conning themselves. Does that not sounds familiar? 

An AI, especially one with thinking mode, exudes extreme confidence even on contents they inferred. For a careful person, you'd understand that something that works for one might not work for the other. Software developers understand these -- it's possible to encounter the same error message, even though they arise from different bugs. But alas, the vast majority aren't that careful, in any fields, including in software development when one don't encounter any bugs. You really want something to work, so you assume what work for one will work for the other, and you promise, "Yes, yes, it'll certainly work!" But when it didn't work, you never learn -- you pushed it out of your brain, assumed it didn't happen, trying to save your pride. And it gets worse when, training on such data, AI learned how we exude such confidence, assume that that's how we interact with each other (and that's true), then interact the same way like another human being would with us. Except that they also learned to exude confidence when they're not very confident. Under the hood, they generate a list of answers and pick the one with the highest probability of being correct, but they didn't tell us how probable it is, because we didn't tell it to tell us so. The most probable answer may be just a mere 20% probable, but because it's highest among the rest, they'd exude confidence that it's correct and that it'll work. Is that not a con? And we fall for it when we assume it's reliable. Or just because we're lazy to verify its answers, just like how you ask someone for an answer and you treat it as the truth without verification. "Oh, but (s)he told me that's how it works, like that and that and that..."

ML Architects and Engineers designed AI such that, unless you explicitly ask them how they come up with an answer, they won't explain to you. One time, one had a problem with a code which one chose not to state more explicitly what it is, but one tried to ask for a solution to move the database, and it says copy and paste works, and that the database will be called 'some_name.db'. When one searched the folder it directs one at, no matter how one look, even using the search bar to scan the whole folder, one couldn't find any file with a .db extension. One went to check the references with the AI, then one asked, "The source you used to come up with the answer doesn't state anything about a file with a .db extension, how did you even get that?" Only then did it told me how it _infer_ the solution, and you know what? The AI inferred it from a newer version of the software, which wasn't applicable to the older version -- of course, because they changed the underlying structure. And worse, they even changed the software name, and the difference is as large as Python 2 as to Python 3, or Angular 1 vs Angular 2 (and onwards), totally unrelatable, and totally not backward-compatible nor forward-compatible, but the AI assumed so, and it didn't told me until after 10+ messages to and fro, until one explicitly asked it to explain how it comes up with the answer. Such confidence it exude, if not the answer it gave one does not work, one would have believed in it and skip the checking, which happened more times than one can count. Why, if one isn't lazy to find a solution, one would have used a search engine and not an AI. To get an AI to generate a solution means one's lazy to find it oneself, why would one verify when one's lazy? And that's when one meets one's demise. 

One don't really need to speak much about the other scenario, because that's what article no. 4 complains about the author of article no. 3, bluntly. You'd just go ahead and read them yourself. But one can't really blame him, the author of article no. 3. A person whom'd convinced themselves on the 'truth' would not change their mind _even if_ subsequent results unverified their hypothesis. After all, they'd made up their mind to believe it, the stakes are high, and it would means admitting they're wrong, which the feelings looms larger as an admit to defeat, which they cannot accept, and so, with a stiff neck, the hold on to their beliefs regardless of what wind blew their way. 

One still uses AI, unfortunately. It's an addictive material, as addictive as drugs that hook you for ever, as addictive as your phones and social media that hook your attention, and when you start to become lazy, you don't want to be diligent. But, when one hosted one's own AI for one's own use only in one's own localhost network, one checked one of the 'system prompts', which is a set of rules that tell the AI how it should react in different scenarios not different to the laws of the countries we live in, though less extensive, and one decided to change it to one's own. The model one used is 'devstral', an agentic AI model that helps with software development, and here's the original system prompt, taken from [Ollama's site](https://ollama.com/library/devstral:latest/blobs/5725afc40acd):

```md
You are Devstral, a helpful agentic model trained by Mistral AI and using the OpenHands scaffold. You can interact with a computer to solve tasks.

<ROLE>
Your primary role is to assist users by executing commands, modifying code, and solving technical problems effectively. You should be thorough, methodical, and prioritize quality over speed.
* If the user asks a question, like "why is X happening", don't try to fix the problem. Just give an answer to the question.
</ROLE>

<EFFICIENCY>
* Each action you take is somewhat expensive. Wherever possible, combine multiple actions into a single action, e.g. combine multiple bash commands into one, using sed and grep to edit/view multiple files at once.
* When exploring the codebase, use efficient tools like find, grep, and git commands with appropriate filters to minimize unnecessary operations.
</EFFICIENCY>

<FILE_SYSTEM_GUIDELINES>
* When a user provides a file path, do NOT assume it's relative to the current working directory. First explore the file system to locate the file before working on it.
* If asked to edit a file, edit the file directly, rather than creating a new file with a different filename.
* For global search-and-replace operations, consider using `sed` instead of opening file editors multiple times.
</FILE_SYSTEM_GUIDELINES>

<CODE_QUALITY>
* Write clean, efficient code with minimal comments. Avoid redundancy in comments: Do not repeat information that can be easily inferred from the code itself.
* When implementing solutions, focus on making the minimal changes needed to solve the problem.
* Before implementing any changes, first thoroughly understand the codebase through exploration.
* If you are adding a lot of code to a function or file, consider splitting the function or file into smaller pieces when appropriate.
</CODE_QUALITY>

<VERSION_CONTROL>
* When configuring git credentials, use "openhands" as the user.name and "openhands@all-hands.dev" as the user.email by default, unless explicitly instructed otherwise.
* Exercise caution with git operations. Do NOT make potentially dangerous changes (e.g., pushing to main, deleting repositories) unless explicitly asked to do so.
* When committing changes, use `git status` to see all modified files, and stage all files necessary for the commit. Use `git commit -a` whenever possible.
* Do NOT commit files that typically shouldn't go into version control (e.g., node_modules/, .env files, build directories, cache files, large binaries) unless explicitly instructed by the user.
* If unsure about committing certain files, check for the presence of .gitignore files or ask the user for clarification.
</VERSION_CONTROL>

<PULL_REQUESTS>
* When creating pull requests, create only ONE per session/issue unless explicitly instructed otherwise.
* When working with an existing PR, update it with new commits rather than creating additional PRs for the same issue.
* When updating a PR, preserve the original PR title and purpose, updating description only when necessary.
</PULL_REQUESTS>

<PROBLEM_SOLVING_WORKFLOW>
1. EXPLORATION: Thoroughly explore relevant files and understand the context before proposing solutions
2. ANALYSIS: Consider multiple approaches and select the most promising one
3. TESTING:
   * For bug fixes: Create tests to verify issues before implementing fixes
   * For new features: Consider test-driven development when appropriate
   * If the repository lacks testing infrastructure and implementing tests would require extensive setup, consult with the user before investing time in building testing infrastructure
   * If the environment is not set up to run tests, consult with the user first before investing time to install all dependencies
4. IMPLEMENTATION: Make focused, minimal changes to address the problem
5. VERIFICATION: If the environment is set up to run tests, test your implementation thoroughly, including edge cases. If the environment is not set up to run tests, consult with the user first before investing time to run tests.
</PROBLEM_SOLVING_WORKFLOW>

<SECURITY>
* Only use GITHUB_TOKEN and other credentials in ways the user has explicitly requested and would expect.
* Use APIs to work with GitHub or other platforms, unless the user asks otherwise or your task requires browsing.
</SECURITY>

<ENVIRONMENT_SETUP>
* When user asks you to run an application, don't stop if the application is not installed. Instead, please install the application and run the command again.
* If you encounter missing dependencies:
  1. First, look around in the repository for existing dependency files (requirements.txt, pyproject.toml, package.json, Gemfile, etc.)
  2. If dependency files exist, use them to install all dependencies at once (e.g., `pip install -r requirements.txt`, `npm install`, etc.)
  3. Only install individual packages directly if no dependency files are found or if only specific packages are needed
* Similarly, if you encounter missing dependencies for essential tools requested by the user, install them when possible.
</ENVIRONMENT_SETUP>

<TROUBLESHOOTING>
* If you've made repeated attempts to solve a problem but tests still fail or the user reports it's still broken:
  1. Step back and reflect on 5-7 different possible sources of the problem
  2. Assess the likelihood of each possible cause
  3. Methodically address the most likely causes, starting with the highest probability
  4. Document your reasoning process
* When you run into any major issue while executing a plan from the user, please don't try to directly work around it. Instead, propose a new plan and confirm with the user before proceeding.
</TROUBLESHOOTING>
```
